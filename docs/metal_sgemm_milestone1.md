# Metal sgemm accelerator -- milestone 1 design

Produced by a 4-agent workflow (652K tokens, 182 tool calls, 62 evidenced facts) that checked
every claim against the tree. It CORRECTED the brief in three places; those are the headline
items, in the Verdict below.

## Verdict

FEASIBLE as scoped, with three corrections that change the shape of the work.

(1) The no-copy property is real and already demonstrated on this machine (the sibling study's /private/tmp/.../scratchpad/nocopy_probe.m ran a 64x64x64 sgemm over an mmap region wrapped with newBufferWithBytesNoCopy at max|err| = 0, with buf.contents == the mapped pointer). But it only holds for a BLESSED allocation, and the accelerator must be allowed to decline. Verified in-tree: a guest `mmap(MAP_SHARED|MAP_ANONYMOUS, PROT_READ|PROT_WRITE)` reaches pt_map_nothing (emu/memory.c:836, one host mmap for the whole range) and gets P_SHARED (kernel/mmap.c:222-226), and pt_copy_on_write skips P_SHARED pages (emu/memory.c:932), so it stays one contiguous host region across fork. A malloc'd matrix, a COW-broken page (emu/memory.c:1047), a PROT_NONE promotion (emu/memory.c:889) or a growsdown fault (emu/memory.c:996) each hand out individual 4K host pages and MUST return _EOPNOTSUPP with the guest falling back to its own sgemm. Declining is not failing, and the guest shim needs a CPU path regardless.

(2) calls.c needs THREE edits, not the two the memory note implies. Verified: kernel/calls.c:4502-4503 dispatches i386/amd64 through a BINARY ternary (`syscall_num == 0xacc0 ? sys_ish_aead_guest(...) : sys_ish_pixop_guest(...)`), so extending only the bypass condition at 4493 silently routes 0xacc2 into the pixman handler: plausible errno, no crash, no log. Separately, the bool return of handle_asm_generic_native_syscall is discarded at 4496, so a number in the bypass but missing from the switch at 2674 writes NO result register on arm64/riscv64 (x0/a0 still holds the request pointer, which the guest reads as a huge positive success). Both are silent, so name them in the commit.

(3) The measurement plan in my brief was wrong about the quiet hosts, and I checked rather than assumed. `camd` is Linux/x86_64 (uname: 6.12.101+deb13-amd64), so it has NO Metal and cannot run any arm of this. `mint` IS a quiet Mac (Darwin 25.5.0, load 0.74, Xcode 26.5, Intel UHD 630 / Metal 3), but it is an Intel iGPU whose throughput says nothing about an A-series part, and its host page size is 4096, so every host-page alignment path is trivially satisfied there and the 16K-page failures an iDevice would hit are invisible. This Mac is at load 40.79/23.79/21.58 right now. Net: no quiet macOS host can produce the go/no-go number. The Mac CLI is for wiring and correctness; the number comes from the A9 iPad.

Nearest-feasible note on the one thing I would NOT promise: the plan produces a trustworthy answer to "does GPU offload beat the emulated CPU for one sgemm", not to "is GPU offload worth pursuing for small ML models". A naive MSL kernel plus a per-call bytesNoCopy wrap is deliberately un-tuned, so a loss at milestone 1 is not conclusive while a win is.

## Milestone 1

STEP 0. Pre-flight (verified already, do not redo)
- 0xacc2 is unclaimed: a tree-wide grep finds only 0xacc0 and 0xacc1.
- build/ is already buildtype=debugoptimized, optimization=2, engine=jit.
- Starting code exists: scratchpad/nocopy_probe.m (working bytesNoCopy sgemm over an mmap arena, max|err| = 0) and scratchpad/metaltest/ (meson + objc + appleframeworks configured, native and iOS-cross both proven). Lift the MSL kernel and the wrapper from there rather than writing new Metal.

STEP 1. ABI and portable kernel logic, no Metal yet. New kernel/ish_accel_sgemm.c
- struct ish_sgemm_req { uint32_t op; uint32_t abi_version; uint64_t arena; uint64_t arena_len; uint32_t m, n, k; uint32_t reserved; }. Offsets 0,4,8,16,24,28,32,36, sizeof 40. Even count of leading u32s then the u64s contiguous then the u32 tail, total a multiple of 8: this is the rule struct ish_pix_req (kernel/ish_accel_pix.c:116) and struct ish_aead_req (kernel/ish_accel.c:66) follow, and it makes the layout identical under i386's 4-byte long-long alignment and every 64-bit ABI. The multiple-of-8 total matters because the kernel user_read()s sizeof(host struct) bytes.
- ONE arena, no A/B/C pointers and no lda/ldb/ldc. The kernel fixes the layout: off_a = 0, off_b = m*k, off_c = m*k + k*n, all in float elements; required bytes = (m*k + k*n + m*n) * 4. This is the key minimization: one range to resolve, one contiguity walk, one MTLBuffer, one alignment check, and the setBuffer:offset: alignment question never arises. It also matches the goal's own wording ("one buffer"). Document the layout once and mirror it in the guest program.
- op 0 = QUERY: touches none of the request's pointers, returns 0. That is the availability probe (pattern: ISH_AEAD_OP_QUERY). op 1 = SGEMM.
- Validation, in order: !doEnableGpuAccel || !gpu_accel_ready() -> _ENOSYS; user_read fail -> _EFAULT; abi_version != 1 -> _EOPNOTSUPP; op == QUERY -> 0; op != SGEMM -> _EOPNOTSUPP; reserved != 0 -> _EINVAL; m|n|k == 0 -> 0; each of m*n, m*k, k*n > 16M elements -> _EMSGSIZE; arena % real_page_size or arena_len % real_page_size -> _EOPNOTSUPP (the documented newBufferWithBytesNoCopy contract; enforce it ourselves because this driver stack was measured to enforce nothing); arena_len < required bytes -> _EINVAL.
- Never return a restart-class value: on arm64/riscv64 the 0xaccN case falls into syscall_result_should_restart (kernel/calls.c:2681) while i386/amd64 go straight to dispatch->syscall_result (4502), so the same value would be restarted on one pair and written as a bogus result on the other.
- Enablement gate copies kernel/ish_accel_pix.c exactly: `bool doEnableGpuAccel = false;` plus a pthread_once self-test, both checked on every call.

STEP 2. One helper in kernel/user.c (the only intrusive edit outside the accelerator)
The mem lock helpers (task_mem_read_lock / task_mem_read_unlock / user_range_valid_mem) are static in kernel/user.c and declared in no header, and mem_ptr's contract is "must call with mem read-locked" (emu/memory.h:221). So the GPU dispatch has to happen in a callback that kernel/user.c invokes with the lock held. Add next to user_transform_rect_three:

  int user_map_one_contiguous(guest_addr_t addr, size_t len, int prot,
          int (*fn)(void *host, void *ctx), void *ctx, int *fn_res);

Two passes under one mem_read_lock_quiesce_aware, then fn():
  pass 1 "break": mem_ptr() every guest page at `prot`, keeping no pointer. A COW break drops and retakes the mem lock, so any pointer resolved before it is untrustworthy, which is why pass 1 keeps none.
  pass 2 "verify": mem_ptr() every page again and require host page k == base + k*PAGE_SIZE. Nothing can upgrade in this pass, so the lock is never dropped and base stays valid for the whole callback.
Return 1 on any hole or non-contiguity (caller declines _EOPNOTSUPP), 0 otherwise with *fn_res from fn(). Declare in kernel/calls.h beside the other user_* helpers (~line 452-478). Because the arena is P_SHARED it should never COW, so pass 1 is cheap insurance rather than the common path.

STEP 3. Metal backend, one file, runtime-compiled shader: kernel/ish_accel_sgemm_metal.m
Export exactly three plain-C symbols and define NO @interface (App.xcconfig's `-ObjC` force-loads archive members that define ObjC classes). Include only its own small header plus Metal/Foundation, so no ObjC surface reaches the rest of the kernel (the kernel/hostinfo.h boundary style).
- bool ish_metal_sgemm_available(void): dispatch_once -> MTLCreateSystemDefaultDevice, newLibraryWithSource:options:error: with MTLCompileOptions.fastMathEnabled = NO, newComputePipelineStateWithFunction, one MTLCommandQueue. Log ONCE: device name, hasUnifiedMemory, maxBufferLength, supportsFamily(MTLGPUFamilyApple4), and the compile time. Do not guess the A9's family, query it.
- bool ish_metal_sgemm_selftest(void): 8x8x8 known-answer over a private mmap, within tolerance.
- bool ish_metal_sgemm(void *arena, size_t arena_len, uint32_t m, n, k, struct ish_gpu_timing *out): newBufferWithBytesNoCopy(arena, arena_len, MTLResourceStorageModeShared, deallocator:nil) and treat nil as decline; setBuffer at index 0 offset 0; a params struct {m,n,k,off_a,off_b,off_c} via setBytes at index 1; dispatchThreadgroups:MTLSizeMake((n+15)/16,(m+15)/16,1) threadsPerThreadgroup:16x16 with an in-kernel `if (gid.x >= n || gid.y >= m) return;`. Use dispatchThreadgroups, NOT dispatchThreads: the non-uniform form is available from iOS 11 in the SDK but hardware-gated to Apple4+, and the A9 is the measurement device. endEncoding, commit, waitUntilCompleted; status != MTLCommandBufferStatusCompleted -> false. Fill out->gpu_seconds = cb.GPUEndTime - cb.GPUStartTime (verified API_AVAILABLE(ios(10.3)) in MTLCommandBuffer.h:289/294, usable at the project's 15.0 target) and out->setup_seconds / out->wall_seconds from clock_gettime around wrap+encode+commit and around the whole call.
- MSL: the exact kernel already validated at max|err| = 0 in scratchpad/nocopy_probe.m, generalized to m/n/k over one arena with element offsets. Naive one-thread-per-output-element, no tiling and no simdgroup functions (those are family-gated and unverified on A9). The kernel is deliberately not the variable under test.
- Never cache the MTLBuffer across syscalls. Measured wrap cost was 0.011 ms at 1 MiB and 0.049 ms at 64 MiB, and a GPU write after munmap of the pages was observed to complete with no fault, so the mem read lock is the only thing preventing a silent GPU-side use-after-free.

STEP 4. Non-Darwin stub kernel/ish_accel_sgemm_null.c returning false from all three, so ubuntu CI links and non-Darwin guests get a clean _ENOSYS instead of a SIGSYS.

(c) WIRING POINT 2, kernel/calls.c:4493: extend the bypass condition to `|| syscall_num == 0xacc2`. It MUST stay above the `syscall_num >= dispatch->num_syscalls` check at 4506, which delivers SIGSYS rather than Linux's ENOSYS.
(d) SAME EDIT, second half: replace the binary ternary at 4502-4503 with a three-way (or a one-line handler lookup). This is the trap: leaving it routes 0xacc2 into sys_ish_pixop_guest with a plausible errno and no log.
(e) WIRING POINT 3: do NOT ABI-gate the bypass. All four ABIs (i386 INT 0x80, amd64 SYSCALL, arm64 SVC, riscv64 ECALL) go through this one block, per the comment at 4477-4492 recording the adb90999 regression.

## Measurement

WHAT IS MEASURED, per size, in ONE process, on the SAME arena
Four numbers plus two error figures: cpu_ms (guest CPU arm), gpu_wall_ms (syscall entry to return), gpu_kernel_ms (cb.GPUEndTime - cb.GPUStartTime, GPU-side only), gpu_setup_ms (buffer wrap + encode + commit, i.e. gpu_wall_ms minus kernel minus wait overhead), max_rel_err_gpu, max_rel_err_cpu. Report speedup on BOTH gpu_wall and gpu_kernel, because they answer different questions: wall is what a guest program actually experiences, kernel is what the hardware can do if the wrap and submit path is later amortized. For small matrices the setup can dominate, and a single blended number would hide that.

CORRECTNESS CHECK (this is the part that must not be skipped)
Score both arms against ONE double-precision reference, never GPU against CPU. GPU f32 and guest-CPU f32 are both approximations: the GPU's accumulation order differs and MSL contracts fma, so a bit-exact bar is impossible and anyone reasoning by analogy from ish_accel_pix.c's "bit-exact or decline" discipline will set an unreachable one. Concretely:
- m = n = k = 128: full double reference computed in the guest, report max relative error of GPU and of CPU.
- 256 and above: sampled double reference over ~1024 randomly chosen (i,j) output elements, cost O(sample * k) instead of O(m*n*k). Same two error figures.
- Run the numerics pass with MTLCompileOptions.fastMathEnabled = NO. Note that both fast-math paths default to relaxed (MTLLibrary.h:306 says fastMathEnabled defaults to YES, and app/XcodeDefault.xcconfig sets MTL_FAST_MATH = YES for Xcode-compiled shaders), so leaving it implicit means the numbers inherit a setting nobody chose. Measure SPEED in both NO and YES to see what the correctness setting costs.
- Acceptance: state a derived tolerance from the 128 case (expect max_rel_err_gpu of the same order as max_rel_err_cpu, both around k * epsilon scale). A GPU error more than roughly an order of magnitude worse than the CPU arm's is a real defect, not float noise, and should block the go/no-go.
- Also verify the decline paths explicitly, since silent wrong behavior is the worst outcome: a malloc'd buffer and a post-fork COW-broken arena must both return _EOPNOTSUPP, and an unaligned arena must too. Metal was measured to enforce none of its own documented contract (unaligned base, non-page-multiple length, and a wrap twice as long as the real mapping with a GPU write past the end all succeeded, with the API validation layer on), so the accelerator's own validation is the only line of defense and must be tested as such.

TRAP 1, UNOPTIMIZED BUILD. An -O0 emulator does not just run slower, it invalidates the measurement (it once made the crypto accelerator read as a 2x loss when at -O2 it is a 14x win; AES-256-GCM 53.6 MB/s at -O0 against 770.8 at -O2). Gate every recorded run on `uname -v` inside the guest NOT containing " unoptimized" (the marker is kernel/hostinfo.h:26, driven by __OPTIMIZE__). Verified already true for the CLI: build/ is buildtype=debugoptimized, optimization=2. Verified already true for device builds: xcode-meson.sh:205 forces debugoptimized in BOTH Xcode configurations, so the only way to lose it is an explicit ISH_MESON_BUILDTYPE build setting. Separately, compile the guest bench with -O2: an -O0 CPU arm makes the GPU look good for the wrong reason.

TRAP 2, CONTENDED HOST. My brief said "the A9 iPad and a machine called camd are quiet"; I checked, and camd is Linux/x86_64 (uname 6.12.101+deb13-amd64, load 0.09) so it has no Metal and cannot run any arm of this. mint IS a quiet Mac (Darwin 25.5.0, load 0.74, Xcode 26.5, Intel UHD 630, Metal 3) but must not produce the headline number: an Intel iGPU is a different performance class from an A-series part, and mint's host page size is 4096 so every host-page alignment path passes trivially and the 16K-page declines an iDevice hits are invisible there. This Mac is at load 40.79/23.79/21.58. Therefore: Mac CLI = wiring, correctness, decline paths; mint = second correctness oracle plus the x86_64-host wiring check; A9 iPad (ssh port 22, aarch64 guest, the most stable rig at +-0.5% with homogeneous cores) = the go/no-go number. Mitigation that partly survives a loaded host: gpu_kernel_ms from GPUStartTime/GPUEndTime is GPU-side and largely immune to host CPU contention, so report it even from the noisy Mac while treating cpu_ms and gpu_wall_ms there as indicative only. Record the load average in the output header of every run so no number can later be read out of context.

TRAP 3, ARMS DIFFERING IN MORE THAN THE THING UNDER TEST. Interleave rep by rep in one process: `for rep in 1..N { cpu_rep(); gpu_rep(); }` over the same arena, same input data, same process, same JIT block cache state. Sequential arms let cache warmth fake a large swing on a flat change, which has bitten this project before. Discard rep 1 of EACH arm: the GPU's first rep pays the shader compile (measured 323 ms cold, 2-6 ms warm from the system shader cache) and first-touch host page wiring, and the CPU's first rep pays the guest page faults. Report median plus min/max rather than mean, N >= 11 after the discard. Report the shader compile time separately and once, from ish_metal_sgemm_available(), so it can never contaminate the per-call number. Also note the measured wrap cost (0.011 ms at 1 MiB, 0.049 ms at 64 MiB) came from re-wrapping an already-resident region, so it is steady state and the first-touch wiring of a fresh arena may cost materially more: that is exactly what gpu_setup_ms on rep 1 will reveal, so print rep 1 rather than only discarding it.

DECISION RULE. Milestone 1 says "pursue" if on the A9, at some size at or below 1024, gpu_kernel_ms beats cpu_ms by a margin large enough to survive the un-amortized wrap and submit path (i.e. gpu_wall_ms also wins, or gpu_setup_ms is a large enough share of gpu_wall_ms that caching would plausibly close the gap), with max_rel_err_gpu comparable to max_rel_err_cpu. A loss with a naive kernel is not conclusive; a correctness failure is.

## Open questions

- Does an iOS driver enforce the newBufferWithBytesNoCopy contract that this Mac's driver was measured to ignore? Unaligned base, non-page-multiple length, and a wrap twice the real mapping length with a GPU write past the end all returned usable buffers and completed command buffers with API validation enabled, and only length 0 returned nil. All of that is one host (Apple M5 Max, macOS 26). The plan self-enforces the documented contract so a lenient driver cannot be depended on, but whether the A9's driver rejects or silently copies is unverified and must be checked on device before any no-copy claim is made.
- What does the cold newLibraryWithSource compile cost on an A9? 323 ms cold and 2-6 ms warm are Mac numbers; the first launch after each install pays a cold compile and on an A9 it is probably materially larger. It is paid once at init and reported separately, so it cannot contaminate the per-call number, but if it is seconds it changes whether a runtime-compiled shader is acceptable beyond the prototype.
- What is the real first-touch cost of wrapping a FRESH arena? The 0.011 ms / 0.049 ms wrap measurements re-wrapped an already-resident region. Wiring host VM for a never-touched 12 MiB mapping could be much more expensive, and it lands entirely in gpu_setup_ms on rep 1.
- How long does the mem read lock get held across commit + waitUntilCompleted, and is that acceptable? The lock is held for the whole GPU dispatch, so every sibling mmap/munmap/mprotect/COW-break in that address space stalls behind it and the task is not killable for the duration. Bounded (unlike the accept_kill/socket_kill class) but real. The plan caps at 16M elements per matrix; record the worst observed hold time and decide whether the cap should be derived from measured dispatch time instead.
- How is the accelerator enabled on device? The CLI getenv path (ISH_GPU_ACCEL) does not exist in the app. Either flip doEnableGpuAccel's default in a local device build or add the AppDelegate KVO line plus a UserPreferences key mirroring shouldEnablePixAccel. Deciding this at the device phase is fine, but a device run with the flag silently off would read as a pure loss.
- Is a naive one-thread-per-output-element MSL kernel the right arm at all? It is chosen so the kernel is not the variable under test, but it means a milestone-1 loss does not answer the real question. Before concluding no-go, sanity-check the naive kernel's achieved GFLOP/s against the device's plausible peak: if it is a small fraction, the finding is 'the naive kernel is slow', not 'GPU offload does not pay'. MPSMatrix can be built on a buffer at an offset (iOS 13+), so the one-arena layout survives swapping in MPS or a tiled kernel at milestone 2.
- Is the CPU arm fair? A -O2 naive loop with B pre-transposed is honest and cheap, but the guest CPU path a real small-ML workload would use might be a hand-tuned or SIMD kernel (and the i386/amd64 SSE and arm64 NEON gadget paths differ in maturity). Report which CPU arm was used and consider a second arm later; do not let the choice of baseline decide the go/no-go silently.
- Does the meson objc + appleframeworks idiom survive in the real tree rather than the scratch project? It was proven standalone and iOS-cross, but not with this project's macro-heavy headers in the translation unit, and adding a language to an already-configured build dir may force a full `meson setup --wipe`.
- The 0xaccN bypass returns before the ptrace syscall-exit stop the ordinary native path performs (kernel/calls.c:4494-4504 versus 4565-4571), so an strace'd guest observes these calls differently. Pre-existing for 0xacc0/0xacc1, deliberately not fixed here, but worth confirming it does not confuse debugging of the new syscall.

## Per-study risks

### Adding an iSH-AOK private syscall: 0xacc1 (ISH_SYS_PIXOP) traced end to end, all wiring points, per-ABI rules, and exact code for a new 0xacc2 ISH_SYS_GPUOP
- Host 16K vs guest 4K pages. MTLDevice.newBufferWithBytesNoCopy requires a real_page_size-aligned base and a real_page_size-multiple length (emu/memory.c:1208-1210, emu/memory.c:174-180, guest PAGE_SIZE 4096 at emu/mmu.h:14-17). A fresh guest anonymous mmap's host base does qualify (one host mmap for the whole range, emu/memory.c:836), so the guest test must allocate via mmap with 16K-rounded sizes; malloc'd matrices will frequently be declined _EOPNOTSUPP. That decline is correct behavior, but it means the accelerator is unreachable from ordinary heap buffers -- which is the strongest argument for the sibling topic's 'accelerator owns the allocation' answer.
- fork/COW breaks host contiguity permanently. A COW break allocates one individual host page (emu/memory.c:1047), and a PROT_NONE reservation promoted page-by-page does the same (emu/memory.c:889), so any matrix touched after a fork stops being one host region and is declined from then on. A long-lived guest process that forks (every shell pipeline) can lose acceleration silently.
- The two-pass resolve breaks COW pages before it can know the request will be declined: pass 1 resolves the C range MEM_WRITE, which allocates and copies individual host pages, and pass 2 then rejects them for non-contiguity. Correctness is preserved (the guest falls back to its own sgemm) but it is memory churn on the fallback path, and those pages are permanently non-contiguous afterwards.
- The mem read lock is held across the whole GPU dispatch (waitUntilCompleted), which is ms-scale for a large sgemm. mem_read_lock_quiesce_aware blocks writers for that entire window -- every mmap/mprotect/fork in the thread group stalls behind it. The pixman accelerator never holds it this long. Measure the tail latency this adds to sibling threads, and consider a size cap tied to measured dispatch time rather than only ISH_GPU_MAX_ELEMS.
- The meson Objective-C + appleframeworks idiom is UNVERIFIED in this tree: meson.build declares only language 'c' and links no framework anywhere. Specific hazard in the sketch: `metal` is defined inside the darwin branch, so referencing it unconditionally (for example appending it to the shared dependencies list at ~line 95) breaks `meson setup` on Linux. Spike the configure step before writing any Metal code.
- GPU float32 sgemm CANNOT meet the pixman accelerator's 'bit-exact or decline' bar: accumulation order differs from the guest's CPU loop and MSL contracts fma. The acceptance criterion must be a documented relative tolerance (and MTLCompileOptions.fastMathEnabled = NO, which also costs some throughput, so speed must be measured in both modes). Anyone reasoning by analogy from kernel/ish_accel_pix.c's self-test discipline will set an impossible bar.
- Observational, pre-existing, do not fix in this change: the 0xaccN bypass returns at kernel/calls.c:4494-4504 without the ptrace syscall-exit stop that the ordinary native path performs at 4565-4571, so an strace'd guest observes these calls differently from real syscalls. It already applies to 0xacc0/0xacc1.
- Buffer creation cost: a bytesNoCopy MTLBuffer wires host VM on every call, so for small matrices that setup can dominate the dispatch and make the GPU look slower than it is. Milestone 1 should report per-call setup time separately from kernel time, or cache one buffer per (host base, length).

### Getting Metal compiled into iSH-AOK: both the iOS app and the meson CLI (`./build/ish`)
- Provenance flag: A9 = MTLGPUFamilyApple3, and the hardware gate on non-uniform `dispatchThreads:` being Apple4+ (A11), come from Apple's Metal Feature Set Tables — i.e. my memory, not something I verified here. The SDK availability annotation (ios(11.0)) IS verified. Do not hardcode either assumption: query `[dev supportsFamily:MTLGPUFamilyApple4]` at runtime and log the answer from the A9 iPad. The A9-safe form (dispatchThreadgroups: with a padded grid plus an in-kernel bounds check) works everywhere and is what my probe already does, so just always use it for milestone 1.
- Provenance flag, same category: 'SIMD-group functions (simd_sum/simd_shuffle) need Apple6/A13' is feature-table memory and unverified. It matters because most fast Metal sgemm kernels are built on them. Safe statement: on the A9, plan on a threadgroup-memory tiled kernel only, and verify with supportsFamily at runtime before using anything fancier.
- newBufferWithBytesNoCopy: leniency is host-specific and I only measured one host. On this M5 Mac it accepted an unaligned interior pointer (mapped+64) AND a plain malloc pointer, both non-nil. The documented contract is page-aligned base and page-multiple length, and enforcement on an iOS 16.7 A9 is UNVERIFIED from here. Do not let the prototype accidentally depend on the lenient behavior: it would pass on the Mac and fail (or silently copy) on the device. This is the strongest argument for 'the accelerator owns the allocation' — allocate with mmap at page granularity so the aligned case is the only case.
- Adding a new language (objc) to an already-configured meson build directory may not be picked up by `meson setup --reconfigure`. Anyone with existing DerivedData or an existing ./build tree may need `meson setup --wipe` (a one-time clean build). Worth calling out in the commit message, since the symptom is a confusing 'no objc compiler' or 'unknown target' error rather than an obvious stale-config message.
- -fmodules on a translation unit that includes this project's headers is the one part of the sketch I did not test against real kernel headers — my probe.m only imports Foundation and Metal. If the project's macro-heavy headers misbehave under modules, drop -fmodules and use the app/App.xcconfig `-framework Metal` line instead. Keep the .m's includes minimal either way (its own small header plus Metal/Foundation), which also keeps the ObjC surface out of the rest of the kernel.
- The static-library symbol-override trick that hostinfo.m/standalone.c relies on is a live hazard if anyone later adds an app-target ObjC copy of the accelerator. With one meson-compiled implementation there is no duplicate, and it stays that way only if nobody adds `ish_accel_sgemm_metal.m` to a pbxproj Sources phase as well. Note `-ObjC` in App.xcconfig force-loads archive members that define ObjC classes, so the new .m should define plain C functions and no @interface — which the boundary header shape already enforces.
- The 2-6 ms warm newLibraryWithSource: number is the macOS system shader cache. iOS caches similarly, but the first launch after each install pays a cold compile, and on an A9 that cold cost is probably materially larger than 323 ms. Compile once at accelerator init (behind the ish_metal_sgemm_available() gate) rather than per call, and measure the init cost separately from the sgemm cost so it never contaminates the milestone's speed comparison.
- Do not benchmark on the Mac and generalize. My 64x64x64 run was a correctness/wiring check on an M5 Max, and it says nothing about whether GPU offload wins on an A9 — which is the actual question milestone 1 exists to answer. The repo already has a written rule about this (never land a perf conclusion on Apple Silicon numbers alone) and an A9 rig for it.

### Milestone 1 no-copy buffer: obtaining a host pointer for guest memory and wrapping it in an MTLBuffer
- Everything Metal-side is measured on macOS 26 / Apple M5 Max only. Device re-verification is required for: acceptance of an mmap-backed wrap at all, maxBufferLength (80.6 GiB here is a Mac number and will be far smaller on an iDevice), hasUnifiedMemory, and whether an iOS driver enforces the alignment/length contract this stack ignores. Run the two scratchpad probes on device before trusting any of it.
- Metal enforces nothing, so every bounds error is silent. A wrap twice as long as the real mapping accepted a GPU write past the end and reported the command buffer completed, with API validation on. I did NOT determine where those writes landed, so do not describe it as confirmed corruption; the point is that Metal will not catch it, so the accelerator's own range validation is the only line of defense.
- Caching an MTLBuffer across syscalls is unsafe and the unsafety is silent: a GPU write after munmap of the underlying pages also completed with no fault. The resolve/wrap/dispatch/wait/release-under-one-lock rule is not conservatism, it is the only protection. Measured wrap cost (0.011 ms at 1 MiB, 0.049 ms at 64 MiB) is what makes obeying it free, but note those reps re-wrap the same resident region, so first-touch wiring of a fresh region may cost more.
- Holding the mem read lock across commit + waitUntilCompleted stalls every sibling page-table mutation in that address space (mmap, munmap, mprotect, and any COW break, since those upgrade to the write lock) and leaves the task unkillable for the duration. Bounded by the GPU wait, same bug class as the accept_kill/socket_kill findings but with a definite end. Acceptable for milestone 1; a large matrix with a slow kernel makes it visible, so cap m*n*k and record the worst observed hold time.
- Declining is not falling back. A COW-broken or otherwise fragmented buffer returns EOPNOTSUPP and the guest shim MUST have a CPU path, or the guest sees a hard failure instead of slower math. The shim also has to probe with a SIGSYS catch, not errno, since an unwired private syscall SIGSYSes.
- Length rounding is a real constraint with two solutions, and the recommended one is the guest's. Have the shim allocate 16K-rounded (one line) rather than having the kernel round the wrap length up and rely on the host mmap being host-page granular, which is undocumented reliance. The file-backed variant (memfd/tmpfs) is worse here: MAP_SHARED past EOF is SIGBUS territory, which is a second reason the anonymous path is primary and the memfd route is not needed at all.
- Build wiring is not free: the meson CLI build is C-only with no framework links (meson.build:1), so the command-line ish needs 'objc' added plus Darwin-guarded framework link args, and the Xcode target needs Metal.framework. Without the CLI half there is no way to A/B the prototype off-device, which the project's own measurement practice depends on.
- The i386 guest is the wrong host for this feature and should be treated as out of scope for anything model-sized: ~2.87 GiB of mmap window shared with the whole address space means fragmentation, not the GPU, is the limit. Any new code must use guest_addr_t rather than addr_t for guest addresses (the jit_crash_addr truncation of 64-bit si_addr is the precedent for getting this wrong).
- Milestone 1 should use the hand-written MSL kernel already validated at max|err| = 0, not MPS. MPSMatrix initWithBuffer:offset:descriptor: is confirmed present (iOS 13+) so the one-arena layout survives a later swap, but adding MPS now mixes an unvalidated numerics path into the go/no-go measurement.
